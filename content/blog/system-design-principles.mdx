"System design" usually means load balancers and database sharding. But a frontend codebase is a system too — it has state that flows through it, boundaries that can fail independently, and pieces that need to evolve without breaking each other. The principles transfer more than people expect.

## Separate what a component does from how it gets its data

The fastest way to make a component impossible to reuse or test is to bake data-fetching directly into it.

```jsx
// Bad — fetching and rendering are welded together
function UserProfile() {
  const [user, setUser] = useState(null);
  useEffect(() => {
    fetchUser().then(setUser);
  }, []);
  return <Avatar user={user} />;
}

// Good — the data source is a swappable concern
function UserProfile() {
  return (
    <UserProvider>
      <UserAvatar />
      <UserDetails />
    </UserProvider>
  );
}
```

This isn't about adding layers for their own sake — a small component doesn't need a provider. It matters once a component is reused somewhere with a different data source, or tested somewhere without a real API.

## Match the state tool to the state's lifetime and scope

The most common architecture mistake isn't picking the "wrong" library — it's using one tool for every kind of state.

- **Local state** (`useState`) — belongs to one component, dies when it unmounts. Form inputs, toggle state.
- **Shared UI state** (Context) — a handful of components need it, it doesn't change often. Theme, auth session.
- **Server state** (React Query / TanStack Query, SWR) — comes from an API, needs caching, retries, and invalidation. Treating it like local state means reinventing a cache badly.
- **Global client state** (Zustand, Redux) — genuinely app-wide, changes frequently, many unrelated components read it. Cart contents, multi-step wizard state.

Server state is the one people most often manage by hand with `useState` + `useEffect`, which quietly reimplements caching, deduplication, and race-condition handling — badly, and one component at a time.

## Design for the failure, not just the happy path

Systems that scale are the ones where one broken piece doesn't take down everything around it.

1. **Composition over inheritance** — small components combined explicitly are easier to reason about than deep component hierarchies.
2. **An abstraction layer over your data fetching** — so a backend contract change is a one-file fix, not a grep-and-replace across the app.
3. **Error boundaries around independent sections** — a broken widget in the sidebar shouldn't blank the whole page.
4. **Lazy loading for anything not needed on first paint** — code-split by route or by feature, not by file size guesswork.

## The mindset shift

Backend system design asks "what happens when this server goes down." Frontend system design asks the same question about a component, a fetch, a piece of state: what happens when it fails, when it's reused somewhere unexpected, or when the data behind it changes shape? Designing for those answers up front is what separates a codebase that can grow from one that needs a rewrite every few features.
